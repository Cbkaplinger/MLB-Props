# Workload personalization experiment card

## ID

`workload_personalization_w0v1`

## Question

Does pitcher-specific workload forecasting improve final K-count
distribution quality beyond a pooled league BF control, when PA
probabilities, lineup reconstruction, aggregation, and assessment
population are held fixed?

## Status

DRAFT — not executed. Requires a new authorized run with the
prediction-save flag to regenerate the keyed PA probabilities and
construct the W0 pooled BF variant.

## Registered cohort

2,509 starts (hash `f77d7a66639ee94a9157244b357487d5f462c6cb0bd4909bbffb44b924db41b7`),
from the count_agg_eval_v1 block_2025H1 eligible population.

## Arms

| Arm | BF probability source | PA probabilities | Aggregation | Scoring |
|---|---|---|---|---|
| W0 (pooled control) | Pooled empirical BF37 from all strictly-prior training rows, add-one smoothing over 37 categories, registered tail conversion | Same keyed values as the accepted baseline (Ref 1 multinomial K marginal) | start_count_pmfs | kc.count_rps |
| W1 (existing workload) | Registered bf-workload-v1 pitcher-specific PMFs (unchanged) | Same keyed values | Same | Same |

## Matched history policy

Both arms use the SAME strictly-prior history policy:
- History = all completed starts with game_date strictly before the
  forecast cutoff.
- W0 pools across all pitchers in the training population.
- W1 uses the pitcher's own completed starts when prior_n >= 10, else
  falls back to the pooled league distribution.
- Smoothing: add-one over 37 categories, both arms.
- Support: 37 categories with overflow, registered tail conversion
  (bf_pmf_from_37, cap 60, geometric tail).

The ONLY difference between W0 and W1 is whether the per-start BF
probability vector is pitcher-specific or pooled from the league.

## Pre-implementation questions — resolved

### Q1: Starter-grain BF history

The existing bf-workload-v1 artifact (registered pin `c9c2762f…`) was
constructed from the chronological strictly-prior pool beginning
2023-01-01, using the pitcher's own counts when prior_n >= 10, else the
pooled league. History is updated after forecasting all starts on a date.
This is the W1 arm; it is NOT regenerated by the experiment.

For W0, the pooled control uses the same strictly-prior history policy
(all completed starts before each forecast cutoff) but collapses to a
single league-level distribution without pitcher-specific filtering.
The pooled distribution is computed from the training-window rows of
the PA source (same y-based population as the states).

### Q2: Exact aggregation reuse

Both arms feed their BF37 vectors through the SAME registered pipeline:
`ad.bf_pmf_from_37` (cap 60, geometric tail) -> `ad.start_count_pmfs(
p9, p9, bf37)` -> `pmf_h3_raw`. The PA K marginal (class-0 probability
per slot) is identical between arms. Only the BF vector differs.

### Q3: Source of shared PA predictions

The keyed PA probabilities from the accepted run were constructed
in-memory but NOT serialized. The per-start parquet saves only scalar
RPS values, not per-PA probability vectors or model coefficients.
Therefore, the workload comparison requires re-executing the model
inference to regenerate the keyed forecast table. This requires a
new authorized run of the same command (same hashes, same cohort)
with a `--save-predictions` flag added to serialize the keyed PA
probability table and both BF variant vectors.

## Limitations

- Development evidence only; not production or betting claim.
- Does not test the frozen incumbent (binary checkpoint).
- Does not test calibration, new features, or taxonomy expansion.
- The BF-vs-outcome relationship is observational; no causal claim
  about removal dynamics or bullpen management.
- The pooled control uses the same smoothing and support conventions,
  so the comparison isolates personalization, not smoothing policy.
